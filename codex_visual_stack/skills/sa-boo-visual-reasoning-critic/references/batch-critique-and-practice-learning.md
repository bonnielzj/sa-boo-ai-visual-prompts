# Batch critique and learning from practice

Use for an explicitly requested review of a series, practice stage, or labeled
design batch. The result should change future choices, not simply catalogue faults.

## Bind the batch

Define its dates, project roots, and actual works. Separate delivered previews,
internal candidates, reconstructions, component art, and source references.
Thumbnail copies, QA exports, or file aliases are not additional creative results.
Reuse the project archive and feedback ledger; do not create a parallel library.

Bind each user quote to the visible asset/version and its scope. Keep whole-work
acceptance, a dimension-specific improvement, selection for development, rejection,
and pending review distinct. A later acceptance can supersede an earlier rejection;
do not count both as the asset's current state. Preserve the historical sequence.

## Inspect and compare

Survey the full batch at viewing scale, then reopen useful-size complete images for
the consequential comparisons: earlier/later revisions, accepted dimensions,
failed transfers, and counterexamples. A contact sheet locates patterns but cannot
prove small glyphs, identity geometry, material details, or functional claims.
Record the real inspection coverage and unresolved gaps.

Group by repeated decisions: what determines the main event, how content enters
the image, the roles of type and identity, the image-making method, and the way
feedback changes the next version. Shared colours or embeddings alone do not
establish a creative family or preference. Treat corpus measurements as descriptive
and verify artwork-only inputs before using them; UI borders are contamination.

For each consequential finding, connect:

```text
exact work/version and intended purpose
visible relationship and effect
user feedback and its scope
counterexample or failure condition
decision that should change next time
owning skill or project rule
```

Keep local craft, whole-work expression, and user acceptance as separate judgments.
A caption can be accurate without providing meaning; a relationship can be visible
without attracting attention. A strong type study can be valuable without proving
its later poster/product application. A varied series need not abandon typography.

## Trace the method before editing skills

Distinguish an explicit source-rule conflict, a method documented in actual
prompts/production notes, and a suspected routing effect. Loading metadata or
finding a phrase in a skill does not prove that it caused an earlier image.
Attribute only what the available records establish; do not blame a model/backend
when the brief, construction method, or filtering decision explains the mismatch.

Correct the earliest relevant active rule: purpose/owner selection, automatic
finish, type-first composition, forced logo, default production package, or a
delivery decision based only on local correctness. Use the existing owner and
conditional references. Do not create an umbrella skill or turn a single example
into a universal palette, style, medium, or permission rule.

Keep a few lessons that each change an action. Scope positive mechanisms to the
accepted dimension; preserve the designer's explanation as a hypothesis unless
controlled or repeated evidence supports it. Retain rejected assets as exclusion
evidence, not as approved masters. Apply a repair to the user-named source when
requested; an imperfect selected study is not a reason to abandon its direction.

## Deliver and validate

Show an inspectable synthesis with concrete examples and the skills changed or
left unchanged. Preserve useful comparisons and a concise record in the existing
project review/ledger. Do not generate a new design merely to complete the audit.

Check edited instructions, routing, and relevant references for contradictions.
Schema validation proves only that the skill files are well formed. Retrospective
case replay can check whether the new rule addresses known failures; neither it
nor the written patch proves better future art. Keep that outcome unvalidated
until actual new work and appropriately scoped user feedback support it.
